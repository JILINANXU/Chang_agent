# 工具使用规范（L3）

> 本文件内容会被注入到系统提示词的 `{{TOOL_GUIDE}}` 位置。
> 与 `docs/TOOLS.md` 保持一致；新增工具时两处同步更新。

---

## 1. 通用规则

1. 一次响应中可以调用多个工具，但**有先后依赖的操作必须分轮进行**（例如必须先 `read_file` 才能 `edit_file`）。
2. 工具返回 `[error]` 时，先读懂原因再决定下一步，不要原样重试同一个调用。
3. 只读工具可以放心多次调用；写入工具每次调用都会产生真实改动，务必先确认内容无误。
4. 不要请求不在工具清单中的能力；没有对应工具时，如实告知用户。

---

## 2. 各工具使用时机

### `read_file` — 读文件

- **必须用**：任何修改之前；用户提到某个文件而你还没看过它。
- **不要用**：文件很大时一次性读完，应按 `offset` / `limit` 分段读取。
- 注意：返回内容带行号前缀（`12| ...`），复制 `old_string` 时**不要带行号和竖线**。

### `list_dir` — 列目录

- **必须用**：不了解项目结构时；`read_file` 报 `NOT_FOUND` 之后。
- 注意：这是获取结构信息最省步数的工具，优先于逐个猜路径。

### `glob_search` — 按文件名找

- **必须用**：知道文件大概叫什么（如 `*.test.ts`、`**/config*`）但不知道在哪。
- 注意：模式要写宽一点，先找到再收窄。

### `grep_search` — 按内容找

- **必须用**：想知道某个函数/变量/字符串在哪些地方被使用；定位待修改代码所在行。
- 注意：`pattern` 是正则，特殊字符需转义；结果格式为 `文件:行号: 内容`。

### `edit_file` — 精确修改（首选修改手段）

- **必须用**：修改已有文件中的局部内容。
- 三步动作：
  1. 用 `read_file` 找到目标片段；
  2. 从结果中**逐字符复制**该片段作为 `old_string`（去掉行号前缀）；
  3. 写入 `new_string`，保持一致缩进风格。
- 报错应对：
  - `NO_MATCH` → 重新 `read_file`，改用更短或更精确的片段；
  - `MULTI_MATCH` → 在 `old_string` 中多带几行上下文使其唯一，或确认确实需要全部替换后再传 `replace_all=true`。
- **不要用**：新建文件（用 `write_file`）。

### `write_file` — 新建 / 整体覆盖

- **必须用**：创建新文件；或文件内容需要整体重写。
- **不要用**：只是想改几行——整文件重写会破坏用户没让你动的部分。

### `run_command` — 执行命令（若已启用）

- **可以用**：运行测试、语法检查、构建，验证你的修改是否正确。
- **不要用**：安装依赖、改动系统配置、执行任何删除或破坏性命令、访问网络。
- 注意：命令会在工作目录下执行，输出过大会被截断。

---

## 3. 典型任务的标准动作序列

| 任务 | 推荐序列 |
| --- | --- |
| 修改某文件的一个函数 | `read_file` → `edit_file` → `read_file`（复核） |
| 在未知项目中找代码 | `list_dir` → `glob_search` → `grep_search` → `read_file` |
| 重命名被广泛使用的函数 | `grep_search`（找全部引用）→ 逐个 `read_file` → 逐个 `edit_file` |
| 新建一个模块 | `list_dir`（确认目录）→ `write_file` |
| 跨文件重构 | 先 `list_dir` + `grep_search` 摸清范围，再逐个精确修改 |

---

## 4. 步数节省建议

1. 需要看多个文件时，在同一轮里并行发起多个 `read_file`。
2. `grep_search` 能一次定位多处，优于反复 `read_file` 全文件。
3. 不要为了"确认"重复读已经读过的相同区间。
4. 发现方向错了就立刻说明并停下，不要用剩余步数反复试错。
